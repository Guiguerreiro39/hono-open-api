## 2. Exact Dialect Differences (`sqlite-core` vs `pg-core`)

| Concept | `drizzle-orm/sqlite-core` (`0.45.x`) | `drizzle-orm/pg-core` (`0.45.x`) | `drizzle-zod@0.8.x` & Migration Impact |
| --- | --- | --- | --- |
| **Boolean** | `integer({ mode: "boolean" })` (0/1 integer storage; JS `boolean`) | `boolean()` (native PG `boolean`) | Both map to `z.boolean()` ([sqlite zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/sqlite/zod.mdx), [pg zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/zod.mdx)). Note: SQLite DDL generated by `drizzle-kit` emits `integer DEFAULT false` (`0000_same_squadron_sinister.sql`). |
| **Timestamp** | `integer({ mode: "timestamp" })` (Unix **seconds** -> `Date`) or `integer({ mode: "timestamp_ms" })` (Unix **ms** -> `Date`). No `.defaultNow()`; SQL defaults require `sql\`(unixepoch())\`` or `sql\`(unixepoch('subsecond') * 1000)\``, or JS `$defaultFn`/`$onUpdate`. | `timestamp({ mode: "date" \| "string", precision?, withTimezone? })`. Default `mode: "date"` (`Date`); default `withTimezone: false` (`timestamp without time zone`). Supports `.defaultNow()` (`DEFAULT now()`). | `integer({ mode: "timestamp" \| "timestamp_ms" })` and `pg.timestamp({ mode: "date" })` map to `z.date()`; `pg.timestamp({ mode: "string" })` maps to string ([pg zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/zod.mdx), [sqlite zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/sqlite/zod.mdx)). Use `{ withTimezone: true }` on PG for UTC-safe instants ([better-auth#9920](https://github.com/better-auth/better-auth/issues/9920)). |
| **Auto-ID PK** | `integer({ mode: "number" }).primaryKey({ autoIncrement: true })` (`INTEGER PRIMARY KEY AUTOINCREMENT`) | `serial().primaryKey()` (legacy 4-byte sequence) **or** `integer().generatedAlwaysAsIdentity().primaryKey()` / `.generatedByDefaultAsIdentity().primaryKey()` (recommended SQL standard). | **Breaking `drizzle-zod` edge case:** `src/db/schema.ts` (`drizzle-zod@0.8.3`) calls `.omit({ id: true })` on `createInsertSchema(tasks)` (`autoIncrement: true`), which compiles when `id` stays an optional key in `Shape`. On PG, `.generatedAlwaysAsIdentity()` marks the column always-generated (excluded from update/insert schemas; [pg zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/zod.mdx), [0.2.0 typebox / 0.3.0 valibot notes](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-valibot/0.3.0.md)), and Zod v4 `ZodObject.omit` rejects keys absent from `Shape` via `Record<Exclude<keyof M, keyof Shape>, never>`. Drizzle v1 docs (`sqlite/zod.mdx`) also omit `autoIncrement` from `createInsertSchema` — drop `id` from `.omit(...)` or use `serial()` / `generatedByDefaultAsIdentity()` if keeping `.omit({ id: true })`. |
| **UUID PK** | `text().primaryKey().$defaultFn(() => crypto.randomUUID())` (no native UUID storage class) | `uuid().defaultRandom().primaryKey()` (`DEFAULT gen_random_uuid()`, native 128-bit `uuid`) or `text().primaryKey()` | `pg.uuid()` maps to `z.string().uuid()` in `drizzle-zod` ([pg zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/zod.mdx)); SQLite `text()` maps to plain `z.string()` unless refined. |
| **JSON** | `text({ mode: "json" }).$type<T>()` or `blob({ mode: "json" }).$type<T>()` (JS `JSON.stringify`/`parse`; empty array SQL default via `sql\`(json_array())\``) | `json().$type<T>()` or `jsonb().$type<T>()` (binary JSON, indexable, `.default({ ... })` emits `'...'::jsonb`) | `.$type<T>()` is compile-time only; `drizzle-zod` maps all JSON modes in both dialects to a generic recursive JSON union (`string \| number \| boolean \| null \| record \| array`). Always pass explicit Zod overrides ([pg zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/zod.mdx)). |
| **Enums** | `text({ enum: ["a", "b"] })` (TS union only; plain `text` DDL, no DB check constraint) | `pgEnum("name", ["a", "b"])` (`CREATE TYPE ... AS ENUM`, must be exported at top level for `drizzle-kit`) **or** `text({ enum: ["a", "b"] })` (plain `text` DDL) | Both `pgEnum` and `text({ enum })` map to `z.enum([...])`. Using `text({ enum })` in PG avoids `ALTER TYPE ... ADD VALUE` migration friction ([Better Auth pg enum snapshot](https://github.com/better-auth/better-auth/blob/v1.6.23/packages/cli/test/__snapshots__/auth-schema-pg-enum.txt)). |
| **`casing: "snake_case"`** | Set in `drizzle({ ..., casing: "snake_case" })` and `defineConfig({ casing: "snake_case" })` | Identical API (`drizzle(..., { casing: "snake_case" })` + `defineConfig({ casing: "snake_case" })`) | Only applies to columns **without** explicit DB name strings (`tasks.createdAt` -> `created_at`). Explicit names (`text("user_id")`) win. `drizzle-zod` always keys off TS property names (`createdAt`, `emailVerified`) ([0.34.0 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-orm/0.34.0.md)). |

### Additional Runtime & Behavioral Gotchas

1. **`$defaultFn` / `$onUpdate` are runtime-only:** As documented in Drizzle `0.30.5`, `$onUpdate` and `$defaultFn` run inside `drizzle-orm` queries only and emit **no** SQL `DEFAULT` or `TRIGGER` DDL in `drizzle-kit` ([0.30.5 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-orm/0.30.5.md)). On PostgreSQL, `createdAt` should pair `.defaultNow()` (or `sql\`now()\``) with `withTimezone: true` so non-Drizzle inserts still get DB defaults.
2. **Timestamp precision mismatch in current schema:** `src/db/schema.ts` uses `integer(..., { mode: "timestamp" })` (Unix **seconds**), whereas Better Auth `1.6.x` SQLite generator uses `mode: "timestamp_ms"` (Unix **milliseconds**). Any future SQLite -> PG data migration must explicitly multiply or interpret Unix epoch units accurately when converting to `timestamptz`.
3. **JSON/Date response serialization:** `createSelectSchema` yields `z.date()` for both `integer({ mode: "timestamp" })` and `pg.timestamp({ mode: "date" })`. Over HTTP JSON (`c.json(row)`), `Date` serializes to an ISO-8601 string. `pg.timestamp({ mode: "string" })` passes raw database strings to and from Postgres without `Date` conversion ([pg column types](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/column-types.mdx)), breaking JS `Date` parity with SQLite `integer({ mode: "timestamp" })`. Keep `mode: "date"` (with `withTimezone: true`) on PG and use `createSchemaFactory({ coerce: { date: true } })` when validating serialized date inputs ([0.7.0 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-zod/0.7.0.md)).
4. **Delete / mutation row counts (`rowsAffected`):** `db.delete(...).where(...)` without `.returning()` returns driver-specific shapes (`ResultSet.rowsAffected` on libSQL vs `QueryResult.rowCount` on `node-postgres` vs `RowList.count` on `postgres-js`). Chaining `.returning({ id: table.id })` works identically on SQLite 3.35+ / libSQL and PostgreSQL and returns `T[]` (`deleted.length === 0`) ([0.29.5 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-orm/0.29.5.md)).
5. **Constraint error codes:** Since `drizzle-orm@0.44.0`, driver failures are wrapped in `DrizzleQueryError` with the underlying driver error on `err.cause` ([0.44.0 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-orm/0.44.0.md)). `src/routes/users/users.handlers.ts` checks `SQLITE_CONSTRAINT_UNIQUE` / `"UNIQUE constraint failed"`; PostgreSQL unique violations instead surface SQLSTATE `"23505"` (`unique_violation`) ([PostgreSQL Error Codes](https://www.postgresql.org/docs/current/errcodes-appendix.html)).

## 3. Shared Helpers, Dialect Isolation & Type Inference (`drizzle-zod` + `zod` v4 + `@hono/zod-openapi`)

### 3.1 Why a Single Union Schema (`SQLiteTable | PgTable`) Breaks Drizzle & `drizzle-zod`

Drizzle ORM intentionally models dialect capabilities at the type level (`SQLiteTableWithColumns` vs `PgTableWithColumns`, distinct dialect symbols). Attempting to share a union table reference (`const tasks = isPg ? pgTasks : sqliteTasks`) or a generic helper over `PgTable | SQLiteTable`:
- Breaks `db.select().from(tasks)` / `db.query.*` overload resolution because a `libsql` or `pg` database instance only accepts tables matching its own dialect brand.
- Breaks `drizzle-zod`'s `createSelectSchema` / `createInsertSchema` / `createUpdateSchema` generic inference (`BuildSchema` over `TTable["_"]["columns"]`), yielding `never` or excessively deep type instantiation errors.

### 3.2 What Works Cleanly

#### A. Shared Domain Constants, Validation Rules & Dialect-Specific Column Helpers
Keep dialect-agnostic primitives shared, and isolate column builders per dialect (`columns.helpers.ts` pattern from Drizzle docs) ([pg schema declaration](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/sql-schema-declaration.mdx)):
- **Shared (`src/db/shared.ts`)**: enum value tuples (`export const ROLE_VALUES = ["admin", "user"] as const`), field length/format refinements (`name: field => field.min(1).max(500)`), JSON payload TS interfaces & Zod schemas, and domain DTO contracts.
- **Per-dialect column helpers**: e.g., `pgTimestamps` (`timestamp({ mode: "date", withTimezone: true }).defaultNow().$onUpdate(() => new Date())`) vs `sqliteTimestamps` (`integer({ mode: "timestamp" }).$defaultFn(() => new Date()).$onUpdate(() => new Date())`).
- Keep TypeScript property names (`createdAt`, `emailVerified`, `userId`) and nullability identical across dialects so `$inferSelect` matches 1:1.

#### B. Dialect-Isolated Schema Files vs Single-Target Cutover
1. **If you need dual-dialect runtime support** (e.g., libSQL in dev/tests, Postgres in prod):
   - Maintain `src/db/sqlite/schema.ts` and `src/db/pg/schema.ts` separately, plus separate `drizzle-kit` configs (`drizzle.sqlite.config.ts` and `drizzle.pg.config.ts` run via `drizzle-kit migrate --config=...`) with separate `out` directories (`src/db/migrations/sqlite` and `src/db/migrations/pg`).
   - Do **not** share `src/db/migrations/meta/_journal.json` across dialects — `_journal.json` hardcodes `"dialect": "sqlite"` and dialect-specific snapshots.
2. **If you are doing a one-time swap (recommended when dual runtime is not mandatory):**
   - Replace `src/db/schema.ts`, `src/db/index.ts`, and `drizzle.config.ts` in place for PostgreSQL, regenerate a clean PG baseline migration folder, and run PostgreSQL locally via Docker so dev/CI tests match production SQL semantics (constraints, `timestamptz`, `jsonb`, `23505`).

#### C. Repository / Service Abstraction Boundary
Route handlers (`src/routes/tasks/tasks.handlers.ts`, `src/routes/users/users.handlers.ts`) currently import `db` and `tasks`/`user` directly and leak `rowsAffected` and `SQLITE_CONSTRAINT_UNIQUE`. Moving persistence behind a small repository boundary (`TaskRepository`, `UserRepository`) keeps Hono route handlers completely dialect-agnostic:
- Repositories expose domain inputs/outputs (e.g., `findById`, `create`, `update`, `deleteById(): Promise<boolean>`) using `.returning()` internally.
- A shared `isUniqueViolation(err)` helper checks `err?.cause?.code === "23505"` alongside SQLite codes (`SQLITE_CONSTRAINT_UNIQUE`, `SQLITE_CONSTRAINT`), eliminating dialect checks from HTTP handlers.

### 3.3 Preserving `drizzle-zod@0.8.x` + `zod` v4 + `@hono/zod-openapi@1.5.x` Type Inference

1. **Why `toZodV4SchemaTyped` + `@ts-expect-error` exists right now:**
   - `drizzle-zod@0.8.3` generates Zod v4 schemas typed against `zod/v4` (`z.ZodObject<...>`), while `src/lib/zod-utils.ts` widens the return type to `z.ZodType<z4.infer<T>>` (from `@hono/zod-openapi`).
   - Casting a `ZodObject` down to `z.ZodType<...>` erases `.partial()`, `.pick()`, and `.omit()` from the TypeScript interface, which is why `src/db/schema.ts` requires `// @ts-expect-error partial exists on zod v4 type` on `insertTasksSchema.partial()` and `insertUserSchema.partial()`.
2. **Official `@hono/zod-openapi` + `drizzle-zod` pattern (`createSchemaFactory`):**
   - Because `@hono/zod-openapi@1.5.1` uses `@asteasolutions/zod-to-openapi@8.5.0` (`zod: ^4.0.0`), Drizzle's documented pattern is binding `drizzle-zod` to `@hono/zod-openapi`'s `z` instance via `createSchemaFactory({ zodInstance: z })` ([drizzle-zod 0.6.0 changelog](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/changelogs/drizzle-zod/0.6.0.md), [Drizzle Zod docs](https://orm.drizzle.team/docs/zod)):
     ```ts
     import { z } from "@hono/zod-openapi";
     import { createSchemaFactory } from "drizzle-zod";

     const { createInsertSchema, createSelectSchema, createUpdateSchema } =
       createSchemaFactory({ zodInstance: z });
     ```
   - This preserves `ZodObject` methods (`.partial()`, `.pick()`, `.omit()`, `.openapi()`) natively without `toZodV4SchemaTyped` or `@ts-expect-error` (and provides `createUpdateSchema(table)` for partial PATCH schemas directly).
   - **Known caveat:** Drizzle issue `#6594` reports that `createSchemaFactory({ zodInstance })` falls back to Drizzle's internal Zod reference for `object`, `json`, `buffer`, and `any` schemas; for `jsonb()` / `text({ mode: "json" })` columns, pass an explicit schema constructed from `@hono/zod-openapi`'s `z` as the field override in `createInsertSchema`/`createSelectSchema`.
3. **Keeping OpenAPI DTO schemas decoupled from dual-dialect tables:**
   - Do **not** generate OpenAPI route schemas from a `PgTable | SQLiteTable` union. Instead:
     - On a single-dialect cutover, generate them from the active table via `createSchemaFactory({ zodInstance: z })`.
     - During a dual-dialect transition, either derive OpenAPI schemas from one canonical schema (or shared `@hono/zod-openapi` DTO schemas) and enforce parity at compile time with `satisfies z.ZodType<typeof tasks.$inferSelect>` (using `typeof pgTasks.$inferSelect` / `typeof sqliteTasks.$inferSelect` equality checks).

## 4. Better Auth (`1.6.x`) `drizzleAdapter`, CLI & `drizzle-kit` Migration Path

### 4.1 `drizzleAdapter` Runtime Configuration (`"sqlite"` vs `"pg"`)

- In `src/lib/auth.ts`, switching runtime dialect requires changing `provider: "sqlite"` to `provider: "pg"` in `drizzleAdapter(db, { provider: "pg", schema })` ([Better Auth Drizzle docs](https://better-auth.com/docs/adapters/drizzle)).
- **Interaction with `casing: "snake_case"`:** Better Auth queries Drizzle models using **TypeScript schema property keys** (`emailVerified`, `createdAt`, `userId`), not physical DB column names ([Better Auth Drizzle docs](https://github.com/better-auth/better-auth/blob/v1.6.23/docs/content/docs/adapters/drizzle.mdx)). Thus `casing: "snake_case"` on `drizzle(...)` or explicit DB column aliases like `emailVerified: boolean("email_verified")` both work without adding `user: { fields: ... }` overrides (you only need `fields` if you rename the JS property, or `usePlural: true` / `schema: { user: schema.users }` if you rename table keys).
- **PG-only `schemaName` option:** On PostgreSQL, `drizzleAdapter(db, { provider: "pg", schemaName: "auth" })` lets Better Auth generate tables inside a dedicated PG schema namespace ([Better Auth Drizzle docs](https://better-auth.com/docs/adapters/drizzle)).
- **Joins (`experimental.joins` in `1.6.x`):** Enabling `experimental: { joins: true }` in `betterAuth(...)` (renamed to `advanced.database.joins` in `1.7`) requires Drizzle `relations(...)` exports in `schema` ([Better Auth 1.7 upgrade guide](https://better-auth.com/docs/guides/1-7-upgrade-guide)). The current `src/db/schema.ts` lacks `relations(...)`, whereas `@better-auth/cli` generates them automatically.

### 4.2 `@better-auth/cli` Schema Generation (`auth generate`)

With the Drizzle adapter, `npx auth migrate` does **not** alter the database; Better Auth delegates DDL migrations to `drizzle-kit` and provides `generate` to emit the Drizzle schema file ([Better Auth CLI docs](https://better-auth.com/docs/concepts/cli)):

```bash
pnpm dlx @better-auth/cli@1.6.25 generate --adapter drizzle --dialect postgresql --output src/db/auth-schema.ts
```

Note `--dialect` (`postgresql`, `sqlite`, or `mysql`) is required when passing `--adapter drizzle` ([Better Auth CLI docs](https://better-auth.com/docs/concepts/cli)).

Comparing Better Auth `1.6.x` CLI snapshots for SQLite vs PostgreSQL against `src/db/schema.ts` reveals concrete diffs:
1. **Booleans:** `integer("email_verified", { mode: "boolean" })` becomes `boolean("email_verified").default(false).notNull()` ([PG plural snapshot](https://github.com/better-auth/better-auth/blob/v1.6.23/packages/cli/test/__snapshots__/auth-schema-drizzle-use-plural.txt)).
2. **Timestamps & defaults:** `src/db/schema.ts` uses `integer("created_at", { mode: "timestamp" })` with no defaults; Better Auth's `1.6.x` PG generator emits `timestamp("created_at").defaultNow().notNull()` and `timestamp("updated_at").defaultNow().$onUpdate(() => new Date()).notNull()` (note: SQLite `1.6.x` CLI snapshots use `mode: "timestamp_ms"`, not `"timestamp"`).
3. **Timezone pitfall (`better-auth#9920`):** Better Auth's PG generator emits bare `timestamp("...")` (`timestamp without time zone`), which risks silent time shifts if Postgres session `TimeZone` is non-UTC. Patch generated auth timestamp columns to `timestamp("...", { withTimezone: true })` ([better-auth#9920](https://github.com/better-auth/better-auth/issues/9920)).
4. **IDs & Enums:** Default PKs remain `text("id").primaryKey()` in both dialects (or `uuid("id").default(sql\`pg_catalog.gen_random_uuid()\`).primaryKey()` in PG if UUID IDs are configured) ([PG UUID snapshot](https://github.com/better-auth/better-auth/blob/v1.6.23/packages/cli/test/__snapshots__/auth-schema-pg-uuid.txt)). Role/enum fields emit `text("role", { enum: [...] })` even on PG ([PG enum snapshot](https://github.com/better-auth/better-auth/blob/v1.6.23/packages/cli/test/__snapshots__/auth-schema-pg-enum.txt)).
5. **Indexes & Relations:** Generated PG schemas add `index("session_userId_idx")`, `index("account_userId_idx")`, `index("verification_identifier_idx")`, and `relations(...)` definitions.

### 4.3 `drizzle-kit` Migration & Cutover Mechanics

1. **Migration history cannot be shared:** `src/db/migrations/meta/_journal.json` specifies `"dialect": "sqlite"`, and `0000_same_squadron_sinister.sql` uses SQLite backticks, `AUTOINCREMENT`, and `integer DEFAULT false`. Point PostgreSQL `drizzle.config.ts` (`dialect: "postgresql"`, remove Turso `authToken`) at a clean PG `out` directory (`src/db/migrations/pg` or reset `src/db/migrations` on one-way cutover) and generate a fresh baseline with `pnpm drizzle-kit generate`.
2. **Data migration requires an ETL script:** `drizzle-kit` migrates DDL only. Existing rows exported from libSQL/SQLite require converting `0`/`1` integers to PG `boolean` and converting `tasks`/`user`/`session` Unix **seconds** integers (`mode: "timestamp"`) to ISO/UTC `timestamptz` values (note: any new columns generated with `timestamp_ms` are milliseconds).
3. **Test harness (`vitest`):** `src/routes/*/*.test.ts` execute `pnpm drizzle-kit push` against `file:test.db`. Moving to PostgreSQL requires updating `drizzle.config.ts` + `.env.test` to target an isolated Postgres database/schema (or an in-process Postgres test runner like PGlite / Testcontainers) and removing `fs.rmSync("test.db")`.
